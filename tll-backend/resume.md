# tll-backend 项目介绍

基于 FastAPI + gRPC 的电商后端，按「HTTP 网关 + gRPC 用户微服务 + Kafka 异步订单链路」分层，覆盖登录鉴权、商品/地址/订单、支付回调与库存一致性。整体思路：入口挡量、缓存扣减、事件解耦、幂等收敛。

技术栈：Python 3.13、FastAPI、gRPC/Protobuf、Tortoise ORM + MySQL、Redis(RedisJSON/Lua)、Kafka、Celery、Consul、Docker Compose

● 鉴权：用无状态 JWT 双令牌兼顾安全与前端体验，access 短、refresh 长，并在 sub 中声明类型，防止 refresh 被当作 access 调用业务接口；过期返 403 让前端静默续期、非法返 401 重新登录；登录不落密码，验证码写 Redis 并带 TTL、用后即删。

● 防超卖：数据库扣库存存在检查-使用竞态和热点行排队，于是把库存前移到 Redis，用 Lua 把「判断余量 + 扣减」合成一次原子操作；缓存未命中回源预热、异常反向回补，落库时再校验一次数据库余量兜底。

● 防重复下单：双击与网络重试会重复扣库存、重复拉起支付，所以先领一次性令牌在 Redis 占位，只有抢到的请求才执行，成功回写结果、失败释放，重复请求直接复用首次结果——把幂等判断从数据库前移到入口。

● 负载均衡：轮询会把流量持续压到慢实例，改为按「在途请求数 + EMA 平滑耗时 + 累计请求数」加权取最小来派发，慢实例自然少接流量；实例列表由注册中心周期刷新，扩缩容无需重启网关。

● 高并发：在线路径全异步，同步客户端和序列化开销移出事件循环；消费路径批量拉取、同事务批量写库、按分区批量提交，把数据库往返和提交成本摊薄，消费端独立进程避免与 Web 抢事件循环。

● 订单消费乱序：支付回调可能先于订单落库，且事件跨 topic、跨分区本就无序，因此不假设顺序：handler 全部幂等，订单不存在时先缓存支付结果再交给任务阶梯重试，配合关闭自动提交，用「至少一次 + 幂等 + 延迟重试」换最终一致性。
